Графовые базы данных (Graph databases) — это тип СУБД, которые хранят данные в виде графа: узлы (nodes), связи (edges) и свойства (properties). Они особенно эффективны, когда важны отношения между объектами.
🔹 Основные элементы
1. Узлы (Nodes)
Представляют сущности
Примеры: пользователь, товар, город, статья.
2. Ребра (Edges)
Определяют связи между сущностями
Примеры: «друг», «купил», «находится в».
3. Свойства (Properties)
Дополнительная информация об узлах и связях
Примеры: имя, возраст, дата создания, количество покупок.
📌 Когда используются графовые базы данных
Графовые базы excel при задачах, связанных с большим количеством взаимосвязей:
Социальные сети (друзья, подписки)
Рекомендательные системы (товары, поведение пользователей)
Навигация, географические данные (карты, маршруты)
Антифрод-системы (подозрительные связи)
Управление знаниями и семантические сети
🔥 Преимущества
Очень быстрые запросы к связям → обход графа эффективнее, чем JOIN'ы в SQL.
Гибкая схема → легко добавлять новые типы узлов/связей.
Наглядность структуры данных.
🧰 Популярные графовые СУБД
СУБД	Особенности
Neo4j	Самая популярная графовая СУБД, язык Cypher
JanusGraph	Масштабируемая, работает с Cassandra/ElasticSearch
ArangoDB	Гибридная (графы + документы + ключ-значение)
TigerGraph	Высокая производительность для больших графов
Amazon Neptune	Облачная графовая БД AWS
📘 Пример запроса (Cypher, Neo4j)

RETURN others;

Векторные хранилища (Vector Stores / Vector Databases) — это базы данных, специально оптимизированные для хранения и поиска векторных представлений данных (эмбеддингов).
Используются в задачах ИИ, семантического поиска, рекомендаций, RAG и др.
🔍 Что такое вектор?
Вектор — это массив чисел (обычно 128–4096+), который представляет смысл текста, изображения, аудио или объекта.
Например: «машина» и «автомобиль» будут иметь близкие векторы — значит, похожий смысл.
🧱 Где применяются векторные хранилища
✔ Семантический поиск
Поиск по смыслу, не по точному совпадению слов.
✔ RAG (Retrieval-Augmented Generation)
Использование внешних данных для LLM через поиск релевантных эмбеддингов.
✔ Рекомендательные системы
Поиск похожих пользователей/товаров.
✔ Обработка изображений и мультимодальность
Поиск похожих изображений по векторным признакам.
✔ Антифрод и кластеризация
Эмбеддинги операций → выявление аномалий.
🧠 Как работает векторная БД
Данные конвертируются в векторы (через модель эмбеддингов).
Хранилище индексирует эти векторы — чаще всего через:
HNSW (Hierarchical Navigable Small World)
IVF / PQ (Faiss)
Annoy
ScaNN
При поиске запрос тоже превращается в вектор.
БД ищет ближайшие векторы по метрикам:
cosine similarity
euclidean distance
dot product

2.2 Графовая модель (Nodes / Edges / свойства)
(Graph DB — Neo4j / Arango)
Узлы (node types) и ключевые свойства
:Document {id, title, visibility, created_at, updated_at, current_version_id}
:DocVersion {id, version_number, content_summary, created_by, created_at}
:Task {id, title, status, priority, assignee, created_at, updated_at}
:Person {id, name, email, role}
:Project {id, name}

:ChangeEvent {id, type, actor, timestamp, metadata}
Связи (edge types)
(:Document)-[:HAS_VERSION]->(:DocVersion)
(:DocVersion)-[:PREV_VERSION]->(:DocVersion) (линейная цепочка)
(:Task)-[:RELATED_TO]->(:Document)
(:Person)-[:CREATED]->(:Document)
(:Person)-[:ASSIGNED]->(:Task)
(:Document)-[:MENTIONS]->(:Person|:Task|:Project)
(:Document)-[:DEPENDS_ON]->(:Document)
(:Task)-[:BLOCKED_BY]->(:Task)
(:DocVersion)-[:EMBEDDED_AS]->(:Embedding)

REASON, confidence, created_at, weight (для strength of association)
2.3 Версионность и event-sourcing (схема)
Светлая модель: DocumentVersion nodes + ChangeEvent stream.
Event store (пример) — каждое изменение записывается как событие:

Event {
  id,
  entity_type,  -- Document/Task/Project
  entity_id,
  event_type,   -- created, updated, field_changed, status_changed
  payload,      -- json diff
  author_id,
  timestamp,
  event_version
}
Graph: (:Entity)-[:HAS_EVENT]->(:Event) and :Event can link to :DocVersion.
3. Индексы, поиск и векторные представления
Exact / metadata search: Postgres + Elastic/OpenSearch (for faceted filters).
Semantic search: Vector DB (Qdrant) indexed with HNSW.
Points: id, vector, payload (title, entity_type, entity_id, project_id, created_at, access_level).
Search metrics: cosine / dot product.
Graph traversals: Neo4j for relationship queries (tracing deps, impact analysis).
Hybrid search flow:
Query → embed → vector search (top-N by semantic)
Filter by metadata in payload (project, visibility)
Expand results via graph: fetch related docs, tasks, authors
Rank by recency / trust score / version freshness
4. API / event flows (конкретика)
Основные REST/GraphQL endpoints (пример)
POST /api/v1/documents — create doc (returns id + initial version)
PUT /api/v1/documents/{id} — update (writes event, creates new DocVersion, updates graph + vector)
GET /api/v1/documents/{id}?at=timestamp — time-machine: get version at timestamp
GET /api/v1/search?query=...&project=...&type=document — semantic + metadata search
POST /api/v1/tasks — create task (auto-link to docs)
POST /api/v1/tasks/{id}/transition — change status (writes event)
GET /api/v1/graph/{entityId}?depth=2 — graph neighborhood
Worker flows
On document create/update:
Persist event to Event Store.
Create new DocVersion node in Graph, link PREV -> NEXT.
Send content to Embedding Service → receive vector.
Upsert vector & payload to Vector DB.
Invoke AI annotators: auto-tags, summary, suggested links.
Update search index (Elastic) for metadata and full-text.
On task create:
Try auto-linking to related docs via semantic similarity (vector DB).
Add graph edges RELATED_TO and create suggested subtasks by LLM.
5. Security, governance и compliance
Auth: OIDC + RBAC. Per-entity ACLs (visibility in payloads).
Encryption: TLS in transit, at-rest encryption for storage.
Audit: Event Store is the source of truth (append-only), signed events optionally.
Data retention / GDPR: soft-delete via events + irreversible purge workflows.
Trust / provenance: every AI-generated change must be labeled, with confidence and origin_model metadata.
6. Operational concerns
Backups: Periodic snapshots for Postgres, Neo4j + VectorDB snapshots, S3 versioning.
Scaling:
Graph DB: cluster or sharding if needed (Arango/Neo4j enterprise).
Vector DB: shard by collections (Qdrant supports partitioning).
Event Store: partition topics (Kafka) or scale Postgres with partitioning.
Observability: instrument latencies for embed calls, vector searches, graph traversals.
Testing: E2E tests that validate versioning/time-travel, and semantic search regression.

11. Риски + как их смягчить
Cost of embeddings: use caching, delta-embeddings, and shorter vectors for non-critical objects.
Graph explosion: prune low-value edges, use weights & TTL for auto-generated suggestions.
Consistency between stores: implement idempotent upserts and a reconciliation job that checks vector DB ↔ graph ↔ event store.
AI hallucinations (auto-changes): never auto-commit changes without human approval; flag AI suggestions and require confirm for high-impact edits.
