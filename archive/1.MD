🧩 Почему текущие инструменты устаревают
1. Они рассчитаны на медленную, ручную работу

🧭 Во что это всё превращается
## 1. Единое пространство данных вместо тасок, документов и страниц
Не будет “тасок”, “страниц” и “проектов”.
Будет единая база смыслов, где каждая единица информации — просто факт/запись/часть контекста.
Это как Notion, но без страниц — только контент, связанный смыслом, а не ссылками.

2. Задачи перестанут быть объектами — станут намерениями
“Добавить таску” → заменяется на “Хочу, чтобы произошло X”.
ИИ:

разлагает на подцели,
уточняет неизвестное,
проверяет риски,
создаёт план (который не надо руками описывать),
выполняет сам или поручает другим агентам.
3. Документация будет генерироваться автоматически
Документирование как действие → исчезнет.
Потому что:
каждый шаг агента и человека логируется,
на основе логов ИИ генерирует структуру,
документы существуют в виде “живых представлений”: summary, full detail, timeline, diff, explanation.
4. Процессы становятся динамическими, а не бюрократическими
Больше не будет статусов “To Do / In Progress / Code Review / Done”.
ИИ сам определяет состояние системы:

что блокируется,
что требует внимания,
что выполняется,
что выполнено.

Исследования показывают, что в рабочих сценариях сотрудники предпочитают «экспертный» стиль общения ИИ – деловой тон, точность и проактивные подсказки
microsoft.com
. Отсюда вытекают следующие принципы UI/UX:
Диалоговый интерфейс: натуральный язык для постановки задач (в духе «сделай X, подготовь Y»). Агенты отвечают чётко и по существу, рекомендуют шаги и уведомляют о важных событиях. Такой формат поддерживает привычный стиль взаимодействия, но свободен от лишней «болтовни»

Информационные дашборды: интуитивные панели с ключевыми показателями (прогресс по целям, ресурсы, приближающиеся дедлайны). Графики и визуальные сводки обновляются автоматически, чтобы сразу увидеть «узкие места» и приоритетные задачи.
Настраиваемые уведомления: система сама решает, кому и когда отправить напоминание или отчёт (например, об обновлении статуса). Это минимизирует переполненные почтовые ящики – в тестах пользователи стали читать на 11% меньше писем

Интеграция с календарём и мессенджерами: переговоры и встречи назначаются ИИ-агентом с учётом занятости и времени учёта глубокого труда. Аудиозаписи и переписка автоматически конспектируются (модуль преобразования речи в текст и NLP-суммаризация). В перспективе могут появиться и «цифровые двойники» (avatars), которые вместо человека участвуют во встречах

Встроенные AI-компоненты и агенты
Продукт включает разнообразные ИИ-модули и мультиагентную платформу. Во главе – большие языковые модели (LLM) с дообучением на отраслевых данных компании (например, GPT-4/GPT-4o, Llama и др.), обладающие памятью контекста. Для комплексных задач формируются «команды» агентов: менеджер-агент ставит цель и делегирует её специализированным агентам-исполнителям

Модуль RAG и хранилище знаний: индексирует корпоративные документы, базы данных и чаты. При запросе ИИ ищет релевантные фрагменты (Retrieval-Augmented Generation) и обеспечивает «негаллюциногенную» выдачу ответов

Интеграции с инструментами: API и плагины для популярных систем (Jira/Trello, Slack/Teams, GitHub, CRM и др.). Пересмотр традиционной структуры (таски, доски, статусы)
Классические концепции «тасков», канбан-досок и фиксированных статусов отходят на второй план. Как отмечает Ю. Аппело, в эпоху ИИ линейные визуализации рабочих потоков устарели: реальные процессы (создание видео или написание книги) носят нелинейный и динамичный характер
medium.com
. Продукт 2025 будет отражать это изменением парадигмы управления:
Нелинейные рабочие потоки: вместо жёстких этапов (To-Do → In Progress → Done) система строит сетевые графы задач. Активность отражается в зависимости от контекста, а не просто по колонкам.
Автообновляемые статусы: пользователю не нужно вручную отмечать «сделано» – ИИ сам отслеживает прогресс по целям и обновляет статус задачи. В итоге исчезает устаревшая иерархия «тасков» – проект становится набором целей и взаимосвязанных результатов.
Фокус на целях, не на процессах: управление проектами ориентируется на конечные метрики (ROI, время до релиза, удовлетворённость клиента), а не на контроль каждого шага. Это даёт больше гибкости: например, задачи могут перераспределяться в процессе без изменения «доски».
Мгновенная ретроспективная картина: вся история изменений и решений хранится, но показывается как единая картинка. Интерфейс демонстрирует «что сделали» и «почему», а не только перечень открытых задач.

B. Структура агентной системы (детали и workflow)
1. Агентная модель — роли
User Agent (UA) — представление пользователя: формулирует намерения, предоставляет approvals.
Orchestrator Agent (OA) — главный координатор; принимает намерения и управляет TaskGraph.
Planner Agent (PA) — строит DAG задач, оценивает риски/сроки, формирует подзадачи.
Dev Agent (DA) — генерирует код, тесты, PR; умеет читать репо.
Integration Agent (IA) — взаимодействует с внешними сервисами (APIs, payments).
QA / Verifier Agent (QA) — автоматические проверки: unit / integration / security.
Docs Agent (DocA) — генерирует документацию, changelog, release notes.
Comm Agent (CommA) — отправляет почты, назначает митинги, делает summary.
Knowledge Agent (KA) — управляет RAG/Embeddings/Knowledge Graph запросами.
Reflection Agent (RA) — после релиза анализирует метрики, находит улучшения.
Human-in-the-loop Moderator (HITL) — человек-контролёр для критичных задач.
2. Протокол взаимодействия агентов
Все агенты общаются через Agent Message Bus (Event Bus). Сообщения имеют структуру:
{
  id: UUID,
  type: "INTENT" | "TASK" | "RESULT" | "NEED-INFO" | "VERDICT",
  payload: {...},
  provenance: {agent_id, context_snapshot, timestamp},
  confidence: 0.0..1.0
}
Оркестратор подписан на INTENT, запускает Planner → создаёт TASK messages в Bus.
Executors подписываются на TASKs по type/labels (e.g., code:, infra:, doc:).
Verifier возвращает VERDICT message с pass/fail + evidence links.
При NEED-INFO: Orchestrator ставит вопрос в UI (или создаёт HITL task).
3. TaskGraph (Planner) — алгоритм (упрощённо)
Input: Intent + Context Snapshot (KA собирает релевантные документы, open PRs, API specs).
Decomposition rules:
Domain rules (templates)
Heuristics (dependency detection via code analysis)
ML classifier (determine whether full automation possible)
Build DAG nodes:
node = {action, tool, estimated_cost, risk_score, owner_agent}
Assign parallelism & ordering (topological sort with priorities)
Output: TaskGraph with metadata (estimates, checks, acceptance criteria)
Commit: create tasks and start execution
4. Loop: Execute → Verify → Reflect
Executor runs node (calls relevant agent/tool).
Result stored in Knowledge Layer with provenance.
QA verifies; if pass → mark node done.
If fail → create new remedial nodes; Orchestrator may escalate to HITL.
5. Примеры prompt’ов / шаблонов для агентов
Planner prompt (сокращённый)
You are Planner. Input: Intent: "Add OAuth2 to mobile app".
Context: repo links, current auth module, API doc.
Task: Decompose into minimal set of steps to deliver feature with tests, migration, docs, and deployment.
Output: JSON TaskGraph: [{id, title, description, tool, agent_type, estimate_hours, risk}]

Dev Agent prompt (для генерации PR)
You are DevAgent (backend: nodejs). Input: Task Node: implement OAuth flow with endpoint /auth/callback.
Context: code snippets, tests, style guides.
Action: produce patch (diff), unit tests, PR description, migration steps.
Constraints: follow lint rules, add docs, do not change other auth flows without justification.
QA Agent prompt
You are QA Agent. Input: PR link, test plan.
Run: static analysis, unit tests, integration with mock provider, pentest check list.
Return: VERDICT with evidence (logs, failing tests). Confidence score.

Для критичных или рискованных задач система требует approval.

Default policy: tasks with risk_score > threshold or with external financial implications require HITL.

Узел становится IN_PROGRESS, когда агент начал работу
